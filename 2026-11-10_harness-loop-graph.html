ハーネス・ループ・グラフ 早わかり

3つの手法の中身、向き不向き、使える場面、そしてそのまま貼れる文を、1ページにまとめます。

結論 ハーネス ループ グラフ 記事と数字 コピーして使う
1

結論

3つとも「指示文の書き方」ではなく、「AIが働く仕組み」の作り方です。

いま効くのはハーネス 使える

できること1体のAIの作業場と安全柵を整えます。守らせたいことは文章ではなく、フックやテストで機械的に止めます。
実務では日々のAI作業は、すでに3つすべての実例になり得ます。まず CLAUDE.md を短くするところからで足ります。

名前の流行より、止め方と証拠を見る 使える

できること完了を機械で判定できるか、外の証拠で確かめているかを見ます。定義はまだ固まっていません。
実務ではグラフエンジニアリングは、2026年7月の冗談まじりの投稿から広まった言葉です。中身は昔からある処理の流れ図の設計です。

「精度18%・費用85%削減」は事実ではない 不要

できること「Microsoft・Stanford・Anthropic が同時に採用し、精度18%向上・費用85%削減」という話は、Turing Post が事実ではないと否定しています。
実務ではその数字は工業図面に関する別の論文のものでした。この話を根拠にはしません。

5つの層の位置づけ

下の層を置きかえるのではなく、積み重なります。多くの記事で共通する整理です（技術ブログの codecentric、DevelopersIO、サーバーワークス、論文サイト arXiv の2本）。

層ひとことで
プロンプト1回の指示文をどう書くか
コンテキストAIに毎回何を見せるか（資料、記憶、道具の説明）
ハーネス1体のAIが働く環境（道具、権限、検査、記録）をどう作るか
ループAIを誰が・いつ・何回動かし、いつ止めるか
グラフ複数のAI・コード・人の承認をどうつなぐか
  • ハーネスの位置は人によって違います。「ループより下の土台」とする整理と、「モデル以外の全部」とする広い使い方があります。
  • ループという言葉も、Claude Code チーム自身が「Xで聞くと答えがいくつも出てくる」と認めています。

おすすめの順番

① ハーネスを固めるCLAUDE.md を目次型で短くし、守らせたいことはフックとテストで止めます。
② 完了条件が書ける作業だけループにする/loop や /schedule は、人がその場で手で始めてください。定期の自動実行からは呼ばないでください。
③ グラフは必要になってから承認や並列の作業が本当にあるときだけ使います。無ければ1本のループで十分です。
2

ハーネスエンジニアリング

1体のAIの作業場と安全柵を作る考え方です。

定義 使える

できることAIがミスをしたら、二度と同じミスをしないよう仕組みを作ります。手段は、決まりを1行足すことと、検査や画面取得などの道具を作ることです。
ほかとの違いハーネスは1体のAIの作業場、ループはその作業場を繰り返し動かす仕組み、グラフは作業場をいくつもつなぐ配線です。

言葉の出どころ

できることMitchell Hashimoto 氏が2026-02-05の個人ブログで、「業界で決まった名前がまだ無いので自分はこう呼んでいる」として使い始めました。
公式の例OpenAI の公式記事（2026-02-11）は、人がコードを1行も書かずに約100万行・約1,500件のプルリクエストを5か月で作った実験を、この名前で呼んでいます。

良いところ

  • 一度作ると以後の全セッションに効きます（個人ブログ、逆瀬川ちゃんのブログは「複利で効く」と表現）。
  • 「お願い」ではなく機械で止めるので、長い作業の途中で指示を忘れても守られます。
  • 同じモデルでも結果が大きく変わる、という報告が多くあります。ただし数値の根拠は記事ごとにまちまちです。

向かないところ

  • 作る手間がかかります。技術記事サイト Zenn のA/Bテストでは、ハーネスありの実装は行数が約3倍に増えました。
  • 「指示の誤解」や「不要な機能の追加」は、どの検査でも確実には捕まえられません（エンジニア記事、martinfowler.com）。
  • モデルが賢くなると不要になる部分がある、という見方もあります（逆瀬川ちゃんのブログ）。

使える場面のパターン

  • 同じ注意を何度もしているときは、決まりに1行足します。それでも破られたら手順書（スキル）へ、さらに破られたらフックで止めます。
  • 削除コマンドや秘密ファイルの編集は、実行前のフックで止めます。
  • 「できました」と言うのにできていないときは、テストが通るまで終わらせないフックを付けます。
  • 長い作業の続きが分からなくなったら、進捗ファイルと git の履歴で引き継ぎます（公式技術記事、Anthropic）。
  • 例: 設定ファイルを生成させるとき、構文チェックを編集のたびに走らせ、エラー文をAIに返して直させます。

ベストプラクティス

  • CLAUDE.md や AGENTS.md は目次にして短く保ちます。目安は OpenAI が約100行、逆瀬川氏は50行以下です。
  • 守らせたいことは文章ではなく、リンター、型チェック、テスト、フックで機械的に止めます。
  • 自作チェックのエラー文には直し方を書きます（公式記事、OpenAI の手法）。
  • リンター設定やテストをAIに書きかえさせません。設定ファイルの編集はフックで禁じます。
  • 速い検査ほど手前に置きます（編集直後、コミット前、CI、人のレビューの順）。
  • 作業開始時の手順を固定します。進捗の一覧は、Markdown より JSON の方が勝手に書きかえられにくいです（公式技術記事、Anthropic）。

何に役立つか 使える

できること設定変更を「AIが案を出す、機械が構文と方針を検査する、人が承認する」形にできます。本番への直接適用はフックで止められます。
実務では「AIの出力を機械で検査する仕組みを作った」は、プロンプトの工夫より説明しやすい成果です。決まりを文章で増やすより、型チェックのように機械で確かめられる形を増やすのが効きます。
3

ループエンジニアリング

1体のAIを、誰が・いつ・何回動かし、いつ止めるかを仕組みにする考え方です。

先に守ること /loop や /schedule は、人がその場で手で始めてください。定期の自動実行から Claude Code を呼ぶことはしないでください。技術ブログ DevelopersIO は、claude -p や Agent SDK が別枠の課金になる場合があると書いています。

定義 使える

できることAIに指示を打つ役を、人からシステムに置きかえます。止める条件を満たすまで作業を繰り返します。
ほかとの違いハーネスは1回の作業の環境、ループはその作業を時間をまたいで繰り返し起動する仕組みです。ループは基本的に1本の流れ、グラフは複数をつなぐ構造です。

言葉の出どころ

できることAddy Osmani 氏のブログ（2026-06-08付。ニュースレター Turing Post は6月7日と記載）が名付け元です。定義は「エージェントにプロンプトを打つ役を、自分からシステムに置きかえること」です。
公式の整理Claude Code チームは4種類に分けています。人が毎回確かめる型、完了条件を渡す型（/goal）、時間で起動する型（/loop、/schedule）、イベントで自動起動する型です。

良いところ

  • 人が張り付かなくても、テストが通るまで直し続けるような作業を任せられます。
  • 朝の振り分けや依存関係の更新など、決まった繰り返し作業に向きます。

向かないところ

  • トークン消費が増えます。DevelopersIO は、Anthropic の実測として「エージェントはチャットの約4倍、複数エージェントは約15倍」を紹介しています。
  • 「読みやすくして」など、機械で判定できる完了条件が書けない作業は、「できました」を繰り返すだけになりがちです。
  • AIがテストを消して通そうとするなどの不正が起きます。
  • ループが速く進むほど、人が中身を理解しないまま変更が増えます（Osmani 氏のブログ、IBM の解説）。
  • 「名前を変えた定期実行にすぎない」という批判も、論文サイト arXiv の論文で紹介されています。同論文は「効果の体系的な証拠はまだ無い」とも書いています。

使える場面のパターン

  • テストが通るまで直す。/goal ./test.sh が exit 0 で終わる。5ターンでだめなら停止（DevelopersIO の例）。
  • 終わる前に検査する門を付ける。Stop フックでテストを走らせ、失敗なら終わらせません。
  • 定期の見回り。/loop 5m 自分のPRを確認し、レビューに対応し、CIの失敗を直す（公式記事、Claude by Anthropic の例）。これは人が手で始めます。
  • 作る係とチェックする係を分け、編集権限の無い検証役に PASS か NEEDS_WORK を返させます。
  • 例: 問題集アプリの問題データを、形式チェックのスクリプトが全件通るまで直させます。

ベストプラクティス

  • 止める条件を、コマンドの終了コードや数値で書きます（「テストが全部通る」「スコア90以上」）。
  • 必ず上限とセットにします（回数、費用、時間）。上限に届いたら人に知らせて止めます。
  • 進まないときの停止も入れます。John Young 氏のブログは「3回続けて変化が無ければ止める」を出発点として挙げています。本人の経験値で、研究結果ではありません。
  • 判定はAIの自己申告ではなく、外のスクリプトで行います。テストファイルはAIが書きかえられないようにします。
  • 状態はファイルに残します。「AIは忘れるが、リポジトリは忘れない」（Osmani 氏）。
  • push、デプロイ、外部送信は人の承認を必須にします。無人のループは別ブランチや別の作業場所で動かします。

何に役立つか 使える

できること「設定案を作る、検証環境で動作確認、失敗なら直す」を、上限付きで自動で回す形が作れます。
実務では定期の作業や Issue の往復は、すでにループです。足りていない点を確かめる価値があるのは、成果物の機械チェックと、失敗時に止めて人へ回す地点です。

定期の自動実行から Claude Code を呼ぶこと 不要

できることサブスクをボットやスクリプトで使うことを、提供元の規約が禁じている場合があります。定期の自動実行から Claude Code を呼ばないでください。
実務では/loop や /schedule を使う場合も、人が手で始める範囲にとどめてください。
4

グラフエンジニアリング

複数のAI、普通のコード、人の承認を、箱とつなぎで設計する考え方です。3つのなかで、定義が最も不確かです。

定義はまだ揺れています あとで

できること作業の単位（AI、普通のコード、人の承認）、次に何をするか、引き継ぐ情報で、処理をつなぎます。
ほかとの違い「ループはグラフの簡易版」（公式ブログ、LangChain）、「グラフはループを含む」（Louis Bouchard 氏のブログ）という整理です。対立ではなく、含む関係です。

言葉の出どころは冗談まじりでした

できること2026-07-18に Peter Steinberger 氏が「まだループの話をしてる？それとももうグラフに移った？」と投稿しました。数時間後、Hamel Husain 氏が「Loop Engineering Is Dead. Enter Graph Engineering」という題の記事を出しましたが、本文はほぼ空（「.」のみ）でした。
新しさLearn Harness Engineering 講座は「2人とも冗談だった」と書いています。LangChain の公式ブログは「新しい考えではない。確立された手法の最新の名前だ」と書いています。LangGraph は2024年からこのモデルを実装しています。

知識グラフ（GraphRAG）とは別物です 不要

できることここで言うグラフは、処理の流れ図の設計です。知識をグラフでつなぐ手法（GraphRAG）とは別物です（Turing Post、サーバーワークス）。
実務では名前だけ見て知識グラフの道具を足す必要はありません。

良いところ

  • 並列にできる作業を同時に走らせられます。
  • 作る係と検査する係を別の文脈に分けられ、自己採点の甘さを避けられます。
  • 途中の状態を保存すれば、失敗した地点から再開できます。
  • 「どこで失敗したか」を後から追いやすくなります。

向かないところ

  • 1つの作業で済むものには過剰です。Turing Post は「ほとんどのエージェントはまだグラフを必要としない」と書いています。
  • 箱を増やすほど、状態管理、デバッグ、費用が増えます。
  • AI同士で確認し合うだけだと、「全部整合しているが何も検証されていない」状態になります（Carlos Perez 氏の指摘、NEC の解説で紹介）。
  • 人のレビュー時間は並列化できません（Osmani 氏の「オーケストレーション税」）。

使える場面のパターン

  • ダイヤモンド型: 調査をいくつかの観点に分けて同時に走らせ、それぞれを検査役が確かめ、最後に1つにまとめます。
  • 振り分け: 簡単な依頼は安いモデル、難しい依頼は強いモデル、判断できないものは人へ回します。
  • 承認の地点: 返金や本番変更など、取り消せない操作の前で止めて、人の承認を待ちます。
  • 例: 複数の係が分かれている作業は、それ自体がグラフです。「必要な印がそろったら次の係が動く」は、承認の地点を持つつなぎです。

ベストプラクティス

  • 先に「決まった段階、承認、並列の作業、段階ごとに違う道具」があるかを確かめます。無ければ1本のループで十分です（ガイド、Bigcircle）。
  • 各箱の入力と出力の形を決めます。自由文ではなく型にします。
  • 検査役には作業役の会話を見せず、成果物と証拠だけを渡します。
  • 外の証拠に必ずつなぎます（実際に走ったテスト、実際の数値、人の確認）。
  • 権限チェックや承認は、プロンプトではなくコードやツールの側に置きます。
  • 並列の幅と費用に上限を付けます。合流するときは「何件返ってきたか」を数え、欠けを見逃しません。

何に役立つか あとで

できること障害調査を「ログ解析・再現・設定確認を並列、結果を合流、修正案、人の承認、適用」という流れ図にする発想は、普段の手順書づくりと同じです。
実務では今の作業の流れを箱とつなぎで書き出すと、「誰がどの成果物を誰に渡すか」「どこで外の証拠と照合するか」の抜けが見つかります。担当同士の確認だけで終わっている箇所が要注意です。

6

コピーして使う

調査が記事の手法をもとに書いた例です。コピーして、そのまま Claude Code に貼れます。/loop や /schedule は、人が手で始めてください。

プロンプト1. ハーネスの点検（毎週1回）
このリポジトリで直近1週間に、あなた（AI）が同じ種類のミスを2回以上したものを git log と PR のコメントから探してください。
それぞれについて、再発を防ぐ方法を「CLAUDE.md に1行足す」「スキルにする」「フックで止める」のどれにするか提案し、理由を1行で書いてください。
まだ何も変更しないでください。
プロンプト2. 完了条件つきの作業（ループ）
/goal ./scripts/check_questions.sh が exit 0 で終わること。
5回試してだめなら止めて、何が残っているかを一覧にしてください。
check_questions.sh とテストデータは変更しないでください。
プロンプト3. 作る係とチェックする係を分ける
修正が終わったと思ったら、evaluator サブエージェントにレビューさせてください。
evaluator には差分とテスト結果だけを渡し、あなたの説明は渡さないでください。
evaluator が PASS を返すまで修正とレビューを繰り返し、3回で通らなければ止めて私に報告してください。
プロンプト4. 並列に調べて検査してまとめる（グラフ）
「[テーマ]」を、[観点1][観点2][観点3]の3つに分けて、別々のサブエージェントで同時に調べてください。
どの結果にも出典URLと日付を付けてください。
それぞれの結果を、調べた係とは別の検査役に渡し、URLが実際に開けて主張と合っているかを確かめさせてください。
確かめられなかったものは「未確認」として分け、最後に1つの報告にまとめてください。
ベストプラクティスのチェック項目
【ハーネス】
- CLAUDE.md / AGENTS.md は目次型で短く保つ（目安: 50行以下、長くても約100行）
- 守らせたいことは文章ではなく、リンター・型チェック・テスト・フックで機械的に止める
- 自作チェックのエラー文に「直し方」を書く
- リンター設定やテストをAIに書きかえさせない（フックで禁止）
- 速い検査ほど手前に置く（編集直後、コミット前、CI、人のレビューの順）
- 作業開始時の手順を固定する（場所の確認、進捗と git ログを読む、基本動作の確認）
- 進捗の一覧は Markdown より JSON の方が書きかえられにくい

【ループ】
- 止める条件を、コマンドの終了コードや数値で書く
- 必ず上限とセットにする（回数、費用、時間）。上限に届いたら人に知らせて止める
- 進まないときの停止も入れる（同じ失敗が続く、2つの状態を行き来する）
- 判定はAIの自己申告ではなく外のスクリプトで行う
- テストファイルはAIが書きかえられないようにする
- 状態はファイルに残す
- push、デプロイ、外部送信は人の承認を必須にする
- 無人のループは別ブランチや別の作業場所で動かす
- /loop や /schedule は人が手で始める（定期の自動実行からは Claude Code を呼ばない）

【グラフ】
- 決まった段階、承認、並列、段階ごとに違う道具が無ければ、1本のループで十分
- 各ノードの入力と出力の形を決める（自由文ではなく型）
- 検査役には作業役の会話を見せず、成果物と証拠だけを渡す
- 外の証拠に必ずつなぐ（実際に走ったテスト、実際の数値、人の確認）
- 権限チェックや承認は、プロンプトではなくコードやツールの側に置く
- 並列の幅と費用に上限を付ける
- 合流するときは「何件返ってきたか」を数え、欠けを見逃さない
CLAUDE.md の例（目次型で短く）
# このリポジトリについて
- 目的: 資格問題集アプリ。詳細は docs/README.md
- テスト: npm test（変更後は必ず実行）
- 問題データの形式チェック: ./scripts/check_questions.sh

# 確認なしでよい作業
- 編集、テストの実行、リンター、ローカルでの検証、調査

# 確認が要る作業
- コミット、push、PR作成、マージ、外部への送信、削除、設定や権限の変更

# やらないこと
- テストファイルとリンター設定を書きかえて通すこと（直すのはコード側）
- 秘密情報（.env など）を読む・書く
設定例. 設定ファイルとテストの書きかえを止めるフック
.claude/settings.json

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Write|Edit|MultiEdit",
        "hooks": [
          { "type": "command", "command": "bash .claude/hooks/protect.sh" }
        ]
      }
    ]
  }
}

.claude/hooks/protect.sh

#!/usr/bin/env bash
file="$(jq -r '.tool_input.file_path // .tool_input.path // empty')"
case "$file" in
  *eslint.config*|*biome.json|*tsconfig.json|*/tests/*|*.env*)
    echo "BLOCKED: $file は保護されています。コード側を直してください。" >&2
    exit 2 ;;
esac
exit 0

（exit 2 で止まり、理由がAIに返ります。仕様は Claude Code Docs の Hooks リファレンスを参照）
設定例. 終わる前にテストを走らせる門
.claude/settings.json

{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/verify.sh" }
        ]
      }
    ]
  }
}

.claude/hooks/verify.sh

#!/usr/bin/env bash
input="$(cat)"
[ "$(echo "$input" | jq -r '.stop_hook_active')" = "true" ] && exit 0
cd "$CLAUDE_PROJECT_DIR" || exit 2
result="$(npm test 2>&1)" && exit 0
echo "テストが失敗しています。通るまで直してください:" >&2
echo "$result" | tail -20 >&2
exit 2

（stop_hook_active の確認は、止め続けて終わらなくなるのを防ぐためです）
設定例. 編集できない検証役（evaluator）
.claude/agents/evaluator.md

---
name: evaluator
description: 完了と言われた作業を疑ってレビューする検証専用の係。編集はしない
tools: Read, Grep, Bash
---
実装した係の説明は信用しないでください。
1. テストを自分で実行し、結果を確かめる
2. テストや設定が書きかえられていないか差分を確かめる
1行目に PASS か NEEDS_WORK だけを書き、2行目以降に根拠を書いてください。
Bash はテストの実行と閲覧だけに使ってください。
依頼文1. ハーネスの最小構成を作る
このリポジトリに最小限のハーネスを入れてください。
(1) CLAUDE.md を50行以内の目次型で作る、(2) 編集のたびにリンターを走らせる PostToolUse フック、
(3) テストが通るまで終わらせない Stop フック、(4) リンター設定とテストの書きかえを止める PreToolUse フック。
作ったら、わざと壊したコードで各フックが動くことを確かめ、結果を見せてください。コミットはまだしないでください。
依頼文2. 設定ファイルの検査ループ
config/ 以下の設定ファイルを検査するスクリプト scripts/lint_config.py を作ってください。
最低限、(1) 必須の項目が欠けていないか、(2) 秘密情報が平文で入っていないか、(3) 値の種類が正しいか、を確かめます。
エラー文には「どの行が」「なぜだめか」「どう直すか」を書いてください。
そのあと、設定を編集するたびにこのスクリプトが走るフックを設定してください。本番環境には一切つながないでください。
依頼文3. 運用のグラフを書き出す
このリポジトリの README と、役割・定期作業の説明を読んで、作業と定期実行のつながりを「ノード（誰・何）」「エッジ（何を誰に渡すか）」「承認の地点」の3つで書き出してください。
そのうえで、担当同士の確認だけで終わっていて、テストなど外の証拠と照合していない箇所を挙げてください。
提案だけで、ファイルは変更しないでください。
依頼文4. 長い作業の引き継ぎ
この機能追加は長くなるので、最初に feature_list.json（各項目に "passes": false）と progress.md を作ってください。
以後は毎回、git log と progress.md を読んでから、未完了の項目を1つだけ進め、テストが通ったら passes を true にし、progress.md に記録してコミット案を見せてください。
feature_list.json の項目を消したり書きかえたりしないでください。
